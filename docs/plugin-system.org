#+TITLE: Autolith Plugin System
#+STARTUP: content

*Status*: intended design. The plugin manager is not implemented. Registration sources carry plugin identity, and the tool registry records a source layer with per-source removal.

* Overview

Autolith plugins let users share code, tools, skills, providers, commands, and
MCP servers as ordinary git repositories, outside the Autolith source tree and
without shipping them in the core.

A plugin is a git repository whose root holds one required file,
=manifest.sexp=. The manifest names the plugin and its entry point and declares
its dependencies. Everything else the plugin does, it does from code: skills,
tool registrations, MCP servers, providers, commands, and context contributors
are registered at load time through the same calls built-ins use.

Users choose what is installed. Declarations live in Lisp initialization files
and are gated by an explicit permission. The agent can operate the whole
plugin system through the same gate.

* Decisions

- Installation is user-gated. One permission record per plugin identity plus
  resolved commit covers install, load, disable, update, and remove.
- Plugins are declared from Lisp; users build the dependency tree with function
  calls.
- Declarations are accepted from global, site, and project scopes.
- Third-party plugin code lives in its own package and reaches Autolith only
  through the exported extension surface.
- Plugins register tools, MCP servers, providers, commands, and context
  contributors directly, under their own registration source.
- Plugins may ship their own ASDF systems and dependencies.
  - A dependency conflict has a deterministic contract, not a solver. A plugin
    and its commit resolve once; where two plugins require different commits of
    the same plugin, scope order decides the winner, the losing requirement is
    recorded in the lock, and the load reports it. A manifest may declare
    =:on-conflict :abort= to fail its own plugin instead.
  - Loading is hot; changing what is loaded is not. Removing a plugin or
    changing its code rebuilds the image: a clean base boots, durable state and
    committed mutations are restored, and the new plugin set loads. That is not
    a rollback, and it discards no self-modification.
- The tool schema stays vanilla: a tool carries the existing single
  =:description=.
  - Plugin residency is layered. The global image carries core plus global
    plugins, and a project image is derived from it to add that project's local
    plugins.

* Terms

- *Plugin identity* :: the pair of a plugin's git source and a resolved commit.
- *Resolved commit* :: the exact git object a requested ref points at.
- *Plugin store* :: the per-user checkout directory holding fetched plugins.
- *Plugin lock* :: the record of resolved refs, the transitive plugin graph,
  and checkout paths.
- *Permission record* :: the user's consent to load one plugin identity.
- *Registration source* :: the layer tag every contribution carries, used to
  remove a plugin's contributions as a group.
  - *Plugin image* :: a saved core that already contains a resolved plugin set.
  - *Image layer* :: one rung of the plugin image ladder, from the global image
    down to a project image.

* Plugin repository and manifest

The only required file is =manifest.sexp= at the repository root. No directory
layout is prescribed beyond that; the manifest names an entry point, and the
plugin organizes everything else as it sees fit.

#+BEGIN_SRC lisp
(:manifest-version 1
 :name "my-cool-autolith-plugin"
 :version "0.3.0"
 :entry "src/init.lisp"          ; or :system "my-cool-autolith-plugin"
 :deps ((:plugin "autolith-plugin-utils"
          :git "github.com/example/autolith-plugin-utils"
          :ref (:tag "v1.1.0"))
         (:system "dexador"))
  :on-undefined :abort
  :on-conflict :record)
#+END_SRC

** Manifest reference

| Key                 | Required | Meaning                                             |
|---------------------+----------+-----------------------------------------------------|
| =:manifest-version= | yes      | schema version, checked before anything loads       |
| =:name=             | yes      | plugin name, the default identifier                 |
| =:version=          | no       | human-readable plugin version                       |
| =:entry=            | one of   | path, relative to the root, of a Lisp file to load  |
| =:system=           | one of   | ASDF system name inside the checkout                |
| =:deps=             | no       | plugin and ASDF dependencies                        |
| =:on-undefined=     | no       | =:abort= (default) or =:warn=                       |
| =:on-conflict=      | no       | =:record= (default) or =:abort=                     |

=:entry= and =:system= are alternatives. A plugin that ships an ASD names the
system and brings its own build; a plugin without one names a file. There is no
API-version key: no versioned extension API exists yet, and one is added when
the exported surface is actually versioned.

=:deps= entries are either plugin source specs or ASDF system names:

#+BEGIN_SRC lisp
(:deps ((:plugin "autolith-plugin-utils"
          :git "github.com/example/autolith-plugin-utils"
          :ref (:tag "v1.1.0")
          :hash "a91c04f0")            ; optional exact pin
         (:system "dexador")))
#+END_SRC

Skills, MCP servers, providers, commands, and tools are not declared in the
manifest. They are things a plugin does at load time, so they are registered
from code and carry the plugin's registration source.

* Declaring plugins

=plugin-get= declares intent. It performs no network access and returns a
plugin record in the =declared= state.

#+BEGIN_SRC lisp
;; user init.lisp
(plugin-get :git "github.com/example/my-cool-autolith-plugin"
            :hash "efffff"
            :deps '((:plugin "autolith-plugin-utils"
                      :git "github.com/me/autolith-plugin-utils-fork"
                      :hash "0badc0de"))
            :enabled t
            :on-failure :disable
            :config (lambda (plugin) ...))
#+END_SRC

| Key           | Meaning                                            |
|---------------+----------------------------------------------------|
| =:git=        | repository URL or shorthand                        |
| =:ref=        | =:tag=, =:branch=, =:commit=, or =:version=         |
| =:hash=       | exact commit; equivalent to =:ref (:commit ...)=   |
| =:local=      | path to a development checkout instead of a fetch  |
| =:deps=       | user-level dependency selection, overrides pins    |
| =:enabled=    | start disabled when false                          |
| =:on-failure= | =:disable=, =:abort=, or =:prompt=                 |
| =:config=     | Lisp run after the plugin loads                    |

Declarations are accepted from global and site =init.lisp= and from a project's
=.autolith/= configuration. A project-scoped plugin set applies only inside
trusted directories, matching the existing directory-scope trust model.

* Resolution and the plugin lock

A requested ref resolves once at install and pins. =:hash= and
=:ref (:commit ...)= are exact and never re-resolve. =:tag=, =:branch=, and
=:version= resolve to a commit that is then recorded, so startup is
reproducible offline without contacting the remote again. Re-resolution happens
only on an explicit update.

=plugins.lock= under the state root records, for each declared plugin:

- the requested git source and ref,
- the resolved commit,
- the checkout path in the plugin store,
- the transitive plugin dependency graph,
- the winner wherever the user or Autolith overrode a plugin's own pin.

The lock is machine-managed and regenerated on resolve or update. It is
separate from permissions: the permission store records user consent and
persists until changed, while the lock records resolution state and is rebuilt
whenever a ref is re-resolved. The permission store answers "may this run"; the
lock answers "what did this ref mean last time".
** Dependency conflicts

Two plugins requiring different commits of the same plugin is the only conflict
the lock has to settle. ASDF system dependencies are not versioned, so ASDF
resolves them by finding the first system with that name and there is no
selection to make. Plugin identities, being a git source plus a commit, are the
only things that can genuinely disagree.

There is no solver. Resolving version ranges would mean inventing compatibility
semantics for plugins that declare none, so the contract is deterministic
precedence plus an honest record instead:

1. Requirements are ordered by scope: a user-level =:deps= selection, then
   global, then site, then project, then the declaring plugin's own pin.
2. The first requirement in that order wins and is the resolved commit.
3. Every losing requirement is recorded in the lock beside the winner, with the
   plugin that made it, so the outcome stays inspectable after the fact.
4. The load reports the conflict, naming both requirements and the winner.
5. A manifest that declares =:on-conflict :abort= fails its own plugin rather
   than loading against a dependency it did not pin.

=:on-conflict= defaults to =:record=, so a plugin that merely uses its
dependency tolerates a different commit, and a plugin that needs its pin gets
to insist on one. Either way nothing is chosen silently, and no plugin is
dropped because another plugin wanted something else.

* Permissions

One permission record per plugin identity: the plugin's git source plus its
resolved commit. It covers install, load, disable, update, and remove, and it is
required of the agent and the user alike. The record is stored the way command
permissions already are, as a validated transactional sexp file under the state
root with a lock file.

- A new resolved commit is a new identity and re-prompts.
- Installing a plugin presents its transitive dependencies in the same approval
  view.
- The plugin system is a decision boundary, not a container. Code loaded into
  the active image is exactly as privileged as the image, consistent with the
  existing stance that process separation is not a security claim.

* Loading

1. =init.lisp= evaluates =plugin-get= forms. Plugins enter =declared=.
2. A background job resolves and fetches each approved plugin into the plugin
   store, writing =plugins.lock=. Missing consent prompts and never blocks
   startup.
3. The manager checks =:manifest-version=.
  4. ASDF compiles the plugin. A compile failure, which by ASDF's definition
     includes any non-style warning, raises
     =asdf/lisp-build:compile-file-error= and fails the plugin with its
     description. Undefined-reference diagnostics are collected during this pass
     and judged after the load.
5. It binds the registration source to the plugin identity and loads =:system=
   then =:entry=, or =:entry= alone.
6. =:config= runs after the plugin is loaded, as ordinary user code.

A failure at any step marks the plugin =failed= with its reason and leaves
startup intact. Registry changes roll back through the existing extension
registry transaction; arbitrary Lisp side effects are not reversible, the same
caveat executable filesystem configuration already carries.

** States

=declared= -> =approved= -> =fetching= -> =resolved= -> =loading= ->
=enabled= / =failed= / =disabled=.

** Undefined references

ASDF performs the compile, and its diagnostics are the primary source. There is
no source pre-scan: the manager does not walk defining heads, because the
compiler already knows which references are unresolved, and a hand-written walk
over =defun=, =defgeneric=, and =defclass= heads reproduces the compiler's job
worse than the compiler does.

Two ASDF knobs cover the compile pass:

- =asdf/lisp-build:*compile-file-failure-behaviour*= is bound to =:error=, so a
  compile failure raises =asdf/lisp-build:compile-file-error= and fails the
  plugin. ASDF defines a failure as including any non-style warning, so an
  undefined *variable*, which SBCL signals as a plain =SIMPLE-WARNING=, is
  already a load failure through this path alone.
- A =handler-bind= on =warning= around the compile operation collects the
  remaining style warnings, which ASDF would otherwise only print.

Undefined *functions* and *types* are style warnings, so they reach the handler
rather than the failure path. The manager keeps the reports that are undefined
references and discards the rest. The discriminator is the condition's format
arguments, not its format control: SBCL passes =(kind symbol)=, where =kind= is
=:function=, =:variable=, or =:type=. The format control is a compiled
=SB-FORMAT::FMT-CONTROL= structure rather than a string, so it cannot be
prefix-matched. SBCL also aggregates repeats past
=sb-c::*undefined-warning-limit*=, which is 3, so the first argument is
sometimes a count: both =(count kind symbol)= and =(kind symbol)= occur. No SBCL
predicate helps here, since =sb-c:undefined-warning-p= names an internal
accumulator structure that is not the condition SBCL signals.

Collected names are judged after the load rather than during the compile pass,
because per-file compilation cannot see the plugin as a whole: a file that calls
a function another file defines warns during its own compile. Once the whole
plugin is loaded, each recorded name is re-checked with =fboundp=, =boundp=, or
=find-class= as its kind requires, and only a name still unresolved then is a
failure. =:on-undefined :abort= fails the plugin; =:warn= loads it and records
the unresolved names in =plugin.status=.

Three cases stay outside this and are accepted rather than worked around:

- Undefined *classes*. =defclass= with an unknown superclass compiles with no
  diagnostic at all, so no name is ever recorded and none is checked. Class
  references are invisible to this gate.
- Calls through =funcall= and computed symbols are not statically visible.
- A macro that expands to a reference the compiler never sees, because the macro
  itself is not loaded yet at compile time.

* Registration and removal

A plugin registers through the same calls built-ins use, and the manager tags
every contribution with the plugin's registration source.

#+BEGIN_SRC lisp
(in-package #:my-cool-autolith-plugin)

(register-plugin-tool
 :namespace "deploy" :name "start"
 :description "Start a deployment for one target and stream its status."
 :parameters (json-object "target" (tool-string-property "Deployment target."))
 :function #'start-deployment)

(register-plugin-skill-root (merge-pathnames "docs/skills/" *plugin-root*))

(register-mcp-server
 '(:name "deploy-registry" :transport (:type :stdio :command "deploy-mcp")))

(define-application-command /deploy
  (:name "/deploy" :description "deploy the current workspace"))

(register-plugin-lifecycle :deactivate #'stop-deployment)
#+END_SRC

Disable removes every registration by source and runs =:deactivate= so the
plugin stops its threads, sockets, and workers. It does not remove definitions;
Lisp code is not unloadable.

** Tools

Plugin tools use the existing tool schema: a namespace, a name, one
=:description=, and a JSON Schema. There is no separate short and long
description, and no skill-linked tool documentation.

** Skill roots

Plugin skill roots are registered from code, tagged by plugin source, and
ordered below every declarative scope. Highest to lowest precedence:

| Rank | Root                                                  |
|------+-------------------------------------------------------|
| 1    | project =.autolith/skills/=                           |
| 2    | Autolith user =skills/=                               |
| 3    | shared user =~/.agents/skills/=                       |
| 4    | site =skills/=                                        |
| 5    | plugin-contributed roots, in declaration order        |
| 6    | bundled =skills/=                                     |

Project, user, shared, and site skills therefore win over plugin skills, and
plugin skills win over bundled first-party skills. A plugin skill that shadows
a bundled skill name is reported at load.

* Lifecycle and restart

=plugin.enable= and =plugin.disable= add and remove registrations in place.
=plugin.update= fetches a new commit. Loaded code cannot be removed from a
running image, so removing a plugin, or changing which plugin supplies a name,
is completed by starting a new image rather than by mutating this one.

Two operations look similar and mean different things.

*Rebuild.* =plugin.restart= boots a clean base image, restores durable state,
replays the committed mutation lineage, and loads the declared plugin set as it
now stands. Nothing is reverted: mutations, conversation, memory, and agenda
all survive, and the only thing that changes is which plugins are loaded. Every
removal, update, and conflict resolution completes through this.

*Rollback.* Selecting a retained generation boots that generation's saved image
directly, which is what it means, so self-modifications made after it are gone.
That is correct for a generation rollback and is not a plugin operation.
=plugin.restart= never selects a generation, and the plugin system never
reaches for one.

The distinction matters because the two have different blast radii. A rebuild
costs a boot and keeps the user's work; a rollback costs the self-modifications
made since that generation. Conflating them would let removing a plugin
silently discard live agent changes.

- The loader is idempotent and records, in the live image, which plugins and
  resolved commits are present, so a rebuilt image reconciles declared against
  present instead of double-loading.
- Plugin-owned runtimes join the checkpoint quiesce path and the runtime-close
  ordering, so a checkpoint taken with plugins loaded is clean.
- Windows withholds rollback rather than rebuild; a rebuild there re-executes
  into the base core and replays as above.

* Image layers and project switching

A plugin set is part of what an image is, so a workspace carrying
project-local plugins needs its own image. Images form a ladder, and every rung
is derived from the rung above it rather than rebuilt from source:

| Layer | Contents                                          |
|-------+---------------------------------------------------|
| 1     | tracked source plus the selected mutation commit  |
| 2     | layer 1 plus global and site plugins              |
| 3     | layer 2 plus one project's local plugins          |

Layer 2 is the image a global install builds, and it is what boots wherever a
directory declares no local plugins. Layer 3 is produced by loading layer 2 and
saving, which is why the ladder only descends: a project image is always a child
of the image its parent produced, never a sibling of it.

Consequences worth naming:

- Switching project boots a different image, because the plugin set differs.
  Durable state follows the user rather than the image, so the switch costs a
  boot and nothing else.
- A project image is invalidated when its own plugin set changes, when the
  global image beneath it changes, or when the mutation commit changes. It is a
  cache keyed on all three, not a durable artifact, and it is rebuilt on demand
  when stale.
- Layer 3 is per workspace, so a machine with many plugin-bearing projects
  accumulates one image each. Only layers 1 and 2 are retained deliberately;
  layer 3 is disposable.
- Windows cannot fork and saves an image by exiting through
  =save-lisp-and-die=, so descending a rung there costs a process rather than a
  fork.

* Observability

#+BEGIN_SRC lisp
> (plugins)
  my-cool-autolith-plugin  0.3.0  efffff  enabled   2 tools, 1 mcp, 1 provider
  autolith-plugin-utils    1.1.0  a91c04  enabled   (dependency)
  vault                    main   3f21bd  failed: could not load entry file
#+END_SRC

=plugins= lists each plugin with its version, resolved commit, state, and
contributed counts. Mutating operations are tools and commands behind the
plugin permission: =plugin.install=, =plugin.enable=, =plugin.disable=,
=plugin.update=, =plugin.remove=, =plugin.restart=. =plugin.list= and
=plugin.status= are unrestricted.

* Implementation gaps

- =skill-roots= computes a fixed list; it needs plugin-contributed roots, tagged
  by source and ordered as above.
- Plugin images need a cache key covering the plugin set, the parent image, and
  the mutation commit, plus invalidation when any of the three moves.
- Plugin-owned runtimes must participate in checkpoint quiescence and runtime
  close ordering

* Deferred

- A versioned extension API with a compatibility key in the manifest.
- Two-tier tool metadata (short summary plus detailed description) and
  skill-linked tool documentation.
- Static detection of dynamic calls through =funcall= and computed symbols.
